Container Architecture

The detection pipeline runs as 6 containers on a GCP VM with a Tesla T4 GPU.

Container Image / Build Port Role
pipeline_service-pipeline_backend-1 pipeline_service/Dockerfile 8100 Detection API — video processing, GDINO inference, LLM inventory, WebSocket progress (GPU)
deploy-backend-1 backend/Dockerfile 8000 Backend API — auth, scans CRUD, job dispatch, push notifications, PostgreSQL/SQLite
deploy-rabbitmq-1 rabbitmq:3-management 5672 / 15672 Message broker — pipeline_jobs queue between backend & pipeline service
deploy-frontend-1 frontend/Dockerfile 3000 → 80 React SPA — served via nginx, proxies /api/ requests
gateway nginx:latest 80 / 443 Reverse proxy — TLS termination, routes /api/detection/ → :8100, /api/ → :8000
florence-live Florence model server 8200 Florence live detection — real-time object detection for camera feed
GPU sharing: Pipeline service and backend share a single Tesla T4 (15 GB VRAM). The gateway container uses a bind-mounted nginx config at /home/bharat.bhaskar/gateway/nginx.conf.

Call Sequence

  1. Authenticate — call one of the auth endpoints to get a JWT.
    ↓ save access_token
  2. Submit Video — upload a video for processing.
    Option A (recommended): Single call to POST /api/detection/v1/process-video
    Option B (chunked): POST .../upload/init → POST .../upload/{job_id}/file → POST .../upload/{job_id}/trigger
    ↓ receive job_id
  3. Listen for Progress — connect WebSocket for real-time updates.
    wss://dev.bundlebox.ai/api/detection/v1/ws/{job_id}?token=<jwt>
    ↓ receive progress events until type: "completed"
  4. Get Results — fetch final inventory and evidence images.
    GET /api/detection/v1/upload/{job_id}
    GET /api/detection/v1/upload/{job_id}/images/{name}

3. WebSocket /api/detection/v1/ws

WSS /api/detection/v1/ws/{job_id} Real-time processing progress AUTH ▶

Connection URL

wss://dev.bundlebox.ai/api/detection/v1/ws/{job_id}?token={jwt_token}
Auth is passed via ?token= query parameter (not header) since browsers don't support custom WebSocket headers.

Server → Client Messages

// Job initiated
{ "type": "initiated",  "progress": 0.01, "message": "Process initiated" }

// Progress updates (multiple)
{ "type": "processing", "progress": 0.25, "message": "Extracting frames..." }
{ "type": "processing", "progress": 0.50, "message": "Running detection..." }
{ "type": "processing", "progress": 0.75, "message": "Generating report..." }

// Completed — includes full result payload
{ "type": "completed",  "progress": 1.0,  "message": "Done", "result": { ... } }

// Error
{ "type": "error", "message": "Processing failed: ..." }

Client → Server

Message Response Purpose
"ping" {"type": "pong"} Keep connection alive (send every 30s)

Connection Lifecycle

  • Connection closes with code 1008 if auth fails
  • Auto-reconnect recommended with 3 second delay
  • Server sends pong in response to ping text frames
  • Connection stays open until client disconnects or job completes

4. Error Format & Codes

All error responses follow this format:

{
  "detail": "Human-readable error description"
}
Code Meaning When
400 Bad Request Validation error, invalid input, no file uploaded
401 Unauthorized Missing or invalid auth token
403 Forbidden Authenticated but not owner of this job/scan
404 Not Found Job, scan, or resource doesn't exist
409 Conflict Email already registered
410 Gone Deprecated endpoint (/trigger)
502 Bad Gateway Upstream service failure (Twilio, etc.)
503 Service Unavailable Required service not configured

5. GCP Load Balancer — Route Configuration Guide

BundleBox uses a GCP Application Load Balancer to route traffic from dev.bundlebox.ai to backend services running on a single GCP VM. This section explains the routing architecture and how to add new routes — using the detection pipeline as a worked example.

5.1 Architecture Overview

Client (mobile app / browser)
    │
    ▼
┌─────────────────────────────────────────┐
│  GCP Application Load Balancer          │
│  IP: 34.102.214.243                     │
│  Domain: dev.bundlebox.ai               │
│  SSL: Google-managed certificate        │
│  URL Map: bundlebox-lb                  │
│                                         │
│  Route Rules (by priority):             │
│   /scanner/sc1/*    → dev-scanner       │
│   /scanner/live-*   → dev-scanner       │
│   /crm/*            → crm-backend       │
│   /api/detection/*  → dev-scanner  ← NEW│
│   /auth/*           → vibe-check        │
│   /api/*            → dev-scanner       │
│   /*                → 404 catch-all     │
└─────────────────────┬───────────────────┘
                      │ HTTPS (self-signed)
                      ▼
┌─────────────────────────────────────────┐
│  Gateway Nginx (port 443)               │
│  Container: gateway                     │
│                                         │
│  /api/detection/*  → :8100 (pipeline)   │
│  /api/*            → :8000 (backend)    │
│  /pipeline/*       → :8100 (legacy)     │
│  /live-detection/* → :8200 (florence)   │
│  /*                → :3000 (frontend)   │
└─────────────────────────────────────────┘
Two-layer routing: The GCP LB selects which backend service (i.e. which VM) to send traffic to. The gateway nginx on the VM then routes to the correct container port. Both layers must be configured.

5.2 Key Concepts

Concept Description
URL Map The routing table. Maps URL patterns → backend services. Ours is named bundlebox-lb.
Backend Service A named target (e.g. dev-scanner-backend) pointing to an instance group / NEG. Has its own timeout, health check, and protocol settings.
Host Rule Maps a domain (e.g. dev.bundlebox.ai) to a pathMatcher.
Path Matcher Contains ordered routeRules with priorities. Lower priority number = matched first.
Route Rule A matchRule (prefix or exact path) + action (forward to backend, redirect, or rewrite).
Priority Integer. Rules are evaluated lowest-first. Must be listed in ascending order in the YAML.

5.3 Step-by-Step: Adding a New Route

The following steps show exactly how /api/detection/* was added for the detection pipeline.

Step 1 — Export the current URL map

# Export to a local YAML file
gcloud compute url-maps export bundlebox-lb \
  --global \
  --destination=/tmp/bundlebox-lb.yaml

Step 2 — Inspect existing route rules

Open the YAML and look at the routeRules array inside pathMatchers. Note the highest priority number in use — your new rule must slot in correctly. 

# Existing rules before our change:
# Priority 1-2: /scanner/sc1/*
# Priority 3-4: /scanner/live-detection/*
# Priority 5:   /crm/*
# Priority 7-8: /auth/*
# Priority 100: /* (catch-all)

Step 3 — Add the new route rule

Insert a new routeRule block. For the detection pipeline, we added two rules:

Rule 1: /api/detection/* (priority 6) — specific route for pipeline service 

      - matchRules:
          - prefixMatch: /api/detection/
        priority: 6
        routeAction:
          weightedBackendServices:
            - backendService: https://www.googleapis.com/compute/v1/projects/PROJECT/global/backendServices/dev-scanner-backend
              weight: 100

Rule 2: /api/* (priority 9) — general API catch-all for backend 

      - matchRules:
          - prefixMatch: /api/
        priority: 9
        routeAction:
          weightedBackendServices:
            - backendService: https://www.googleapis.com/compute/v1/projects/PROJECT/global/backendServices/dev-scanner-backend
              weight: 100
Priority ordering matters! /api/detection/ (priority 6) must come before /api/ (priority 9), otherwise the broader /api/ prefix would match first and the detection-specific rule would never trigger.

Step 4 — Validate YAML ordering

GCP requires route rules to be listed in ascending priority order within the YAML file. If they're out of order, the import will fail with: 

HTTPError 400: Invalid value for field 'resource.pathMatchers[0].routeRules[N].priority':
'9'. Within a pathMatcher, a route rule must have a priority that's higher than
the previous route rule's priority

Correct order for our config:

# ✅ Correct: ascending priority in YAML
Priority 1: /scanner/sc1       (redirect)
Priority 2: /scanner/sc1/*     (rewrite → /)
Priority 3: /scanner/live-detection  (redirect)
Priority 4: /scanner/live-detection/* (rewrite)
Priority 5: /crm/*
Priority 6: /api/detection/*    ← NEW
Priority 7: /auth              (redirect)
Priority 8: /auth/*            (rewrite → /)
Priority 9: /api/*             ← NEW
Priority 100: /*               (catch-all)

Step 5 — Import the updated URL map

gcloud compute url-maps import bundlebox-lb \
  --global \
  --source=/tmp/bundlebox-lb.yaml \
  --quiet
The --quiet flag skips the confirmation prompt. The fingerprint field in the YAML provides optimistic concurrency — if someone else modified the URL map since your export, the import will warn (but still succeed today; future gcloud versions may reject stale fingerprints).

Step 6 — Update backend service timeout (if needed)

Detection pipeline jobs can take several minutes. The default 30s backend timeout will kill long requests. We increased it to 600s: 

gcloud compute backend-services update dev-scanner-backend \
  --global \
  --timeout=600
Note: maxStreamDuration in route rules is only supported for INTERNAL_SELF_MANAGED load balancing schemes. For external Application LBs, use the backend service --timeout instead.

Step 7 — Update gateway nginx on the VM

The GCP LB forwards traffic to the VM, but nginx on the VM must also know how to route it to the correct container port. 

# SSH into the VM
gcloud compute ssh bharat.bhaskar@gpu-instance-bundlebox-t4 \
  --zone=us-west3-b --project=second-raceway-477108-k9

# Edit the gateway nginx config (bind-mounted)
vim /home/bharat.bhaskar/gateway/nginx.conf

Add the new location block (order matters — more specific first): 

    # ── Detection API (pipeline service) ──
    location /api/detection/ {
        proxy_pass http://host.docker.internal:8100;
        proxy_http_version 1.1;
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host       $host;
        proxy_read_timeout 600s;
        proxy_send_timeout 600s;
    }

    # ── BundleBox API (backend) ──
    location /api/ {
        proxy_pass http://host.docker.internal:8000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host       $host;
        proxy_read_timeout 600s;
        proxy_send_timeout 600s;
    }
nginx prefix matching: /api/detection/ must appear before /api/ in the config file. nginx uses first-match for location prefix blocks.

Reload nginx without downtime:

docker exec gateway nginx -s reload

Step 8 — Verify end-to-end

# 1. Test through the full chain (LB → nginx → container)
curl -s https://dev.bundlebox.ai/api/detection/v1/health
# → {"status":"ok","service":"pipeline_backend"}

# 2. Verify backend API still works
curl -s -o /dev/null -w "%{http_code}" https://dev.bundlebox.ai/api/v1/health
# → 200

# 3. Verify old prefix is dead
curl -s -o /dev/null -w "%{http_code}" https://dev.bundlebox.ai/pipeline/v1/health
# → 502 (no route on pipeline service for old prefix)

5.4 Common Gotchas

Issue Cause Fix
Import fails with priority error Route rules not in ascending priority order in YAML Reorder the routeRules array so priorities go 1, 2, 3, … ascending
Import fails with maxStreamDuration error maxStreamDuration not supported on external ALBs Remove it from route rules; use --timeout on the backend service instead
502 Bad Gateway after LB update Gateway nginx not updated, or container env var mismatch Add matching location block in nginx config and nginx -s reload
404 on correct URL Container built with old code; env var not picked up Rebuild with docker compose up -d --build; verify with docker exec ... env | grep PREFIX
Broader prefix matches instead of specific Specific rule has higher priority number than general rule Give the more-specific path a lower priority number (matched first)
Edits to nginx config inside container lost on restart Config is baked into image, not bind-mounted Edit the host file and nginx -s reload; or rebuild the image
